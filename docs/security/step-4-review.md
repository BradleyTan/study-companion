# Step 4 security review

Date: 2026-10-19. Reviewer: security-engineer. Branch `claude/step-4`, reviewed against `main` (`git diff main...HEAD`, up to the QA sign-off `83a8541`).
Scope: study timer and session log (`study_sessions`, timer columns on `profiles`, `src/server/actions/timer.ts`), timetable slots (`timetable_slots`, `src/server/actions/timetable.ts`), server-side `.ics` import (`src/lib/timetable/ics.ts`, `import.ts`), the public calendar feed (`src/app/api/calendar/[token]/route.ts`, `src/server/calendar.ts`, `supabaseCalendarFeed`, `src/lib/timetable/feed.ts`, `calendar_links`), `src/server/origin.ts`, the service worker `public/sw.js`, migrations `20261019000001_step4_study_timer.sql` and `20261020000001_step4_timetable_calendar.sql`, the privacy page, and the items QA handed over in `docs/qa/step-4.md` (open issues 3 and 9).

**Verdict: cleared to merge.** There were no critical or high findings. The medium finding (S4-1, CPU cost of a hostile timetable file) and five low findings are fixed on this branch. Three low findings are accepted (table). Nothing was applied to the live database or any live service.

## Findings

| # | Severity | Finding | Where | Status |
|---|---|---|---|---|
| S4-1 | Medium | **A hostile timetable file took about 5 s of server CPU to preview.** `previewImport` parses an uploaded `.ics` (up to 1 MB) and expands every repeat rule over the next 26 weeks. The rule budget (`MAX_STEPS = 200,000`) bounded the steps but not the dates worked out, and each date costs several `Intl` time zone conversions. A 1 MB file of 5,000 events that each repeat daily (`RRULE:FREQ=DAILY;COUNT=100000000`) took **4.8 s**. A file naming thousands of unknown zones also built a new `Intl.DateTimeFormat` on every validity check (1.2 s). Any signed-in student can send this in a loop. Each request blocks the Node event loop and uses the shared free Vercel CPU allowance. The impact is availability only. I benchmarked 10 hostile shapes: daily repeats, huge `COUNT` from 1900, 60,000 `RDATE`s, `EXDATE` lists, 5,000 one-offs, 300,000 nested `BEGIN`s, one 200,000-part folded line, 200,000 quoted parameters, 5,000 zones and 5,000 `RECURRENCE-ID`s. Parsing is linear in every case (under 100 ms). | `src/lib/timetable/import.ts` (`expand`, `planImport`), `src/lib/timetable/dates.ts` (`isValidTimeZone`) | **Fixed** in `7b6d122`. There is now a whole-file budget of 8,000 worked-out dates (`MAX_DATES_WORKED`); events after it count as "over the import limit". A real timetable has a few thousand dates at most within 26 weeks. Dates of a `COUNT` rule well before today are counted but not converted. `isValidTimeZone` remembers its answers (bounded at 2,000). Worst case now: 0.6 s (daily repeats), 0.5 s (many zones), every other shape under 0.4 s. New test in `src/server/actions/timetable.test.ts` with a 2.5 s limit; it fails on the old code (5.5 s). |
| S4-2 | Low (QA 9) | **Sign-in links could follow a spoofed Host header in a real deployment.** Step 4 moved `siteOrigin()` out of `auth.ts` and let it fall back to the Host header in production whenever `DEMO_MODE=1`. But `DEMO_MODE=1` doesn't turn demo mode on when Supabase is configured (`isDemoMode()` is false then). If `DEMO_MODE=1` was ever left in the live environment with `NEXT_PUBLIC_SITE_URL` unset, magic-link and Google sign-in redirects would be built from `X-Forwarded-Host`/`Host`. This weakens T16. The Supabase redirect allow-list is the second line of defence. | `src/server/origin.ts` | **Fixed** in `5b2e2ce`. The fallback now uses `!isDemoMode()`, so only the real in-memory demo (which sends no email) can use the Host header. New `src/server/origin.test.ts`: with Supabase configured and `DEMO_MODE=1`, `siteOrigin()` throws (this test fails on the old code). The e2e production build (demo, no Supabase) still works. |
| S4-3 | Low (QA 3) | **Import Undo worked for any batch at any time on the server.** Only the 6-second toast limited it. A late or replayed call deleted the classes the batch had added. Once a later import had cleared `import_prev`, the call also deleted a class the batch had updated. The call reinstated rows the batch had removed, if they hadn't been purged yet. Supabase also hard-deleted soft-deleted rows of the batch; demo didn't. Only the student's own data is affected, and batch ids are random and pinned to the student. | `src/server/repo/{supabase,demo}.ts` (`applyImport`, `undoImport`), `src/server/actions/timetable.ts` | **Fixed** in `d4f44bf`. Every row an import adds, changes or removes now carries `import_prev {batch, at, added \| removed \| before}`. The next import clears `import_prev` on all of the student's rows, including removed rows waiting for the purge, so only the latest import can be undone. The server refuses an undo more than 5 minutes after the import ("That import can't be undone any more."). Supabase and demo now take back exactly the same rows. New test: an undo of an earlier batch after a newer import, of an unknown batch and after 6 minutes all change nothing; a timely undo works once. |
| S4-4 | Low | **A time zone that isn't real could reach slots and the feed's `TZID`.** `profiles.timezone` can be written by the student directly (the "own profile" policy with an `update` grant), and the database checks only its length. `getProfile` returned it as stored, slots copied it into `tz`, and the feed wrote `tz` into `TZID=` and `TZID:` unescaped. A value like `Europe/London\r\nX-...` would put a line of the student's choice into their own feed. Any value that isn't a time zone made `instantOf` throw, which broke the timetable page and made the feed answer 503. Only the student's own feed and pages are affected. | `src/server/repo/supabase.ts` (`getProfile`), `src/lib/timetable/feed.ts`, `20261020000001_step4_timetable_calendar.sql` | **Fixed** in `31cb0bf`. `getProfile` passes the zone through `safeTimeZone`. `timetable_slots.tz` must match `^[A-Za-z0-9_+/-]{1,64}$`; the Step 4 migration isn't applied live yet, so I edited it in place. `buildFeed` reads any `tz` that isn't a valid zone name as UTC (`feedZone`). Tests: `timetable.test.ts` (`feedZone` and an injected line that doesn't appear in the feed) and `10_rls.sql` (a zone with a line break is refused; this test fails on the old migration). |
| S4-5 | Low | **The public feed did avoidable CPU work on every fetch.** The route needs no sign-in. Every fetch rebuilt each VTIMEZONE from scratch (about 600 `Intl` calls per zone across 11 years) and folded lines with one `TextEncoder` call per character. A feed with 300 slots and 60 skipped weeks each took 330 ms in one zone. Spread over 300 zones it took 1.9 s. Only the student who owns the link, or someone they gave it to, can make it that big. | `src/lib/timetable/feed.ts` (`vtimezone`, `foldLine`) | **Fixed** in `31cb0bf`. VTIMEZONE blocks are remembered per zone and year range (bounded at 2,000). Folding counts UTF-8 bytes directly and skips lines of 25 characters or fewer. Results: 78 ms for one zone, about 50 ms for 300 zones once warm. The first fetch on a new server instance still takes about 1.5 s for 300 zones. Test: a byte-exact fold for multi-byte text, and a second build of a 100-zone feed in under 250 ms. |
| S4-6 | Low | **The public feed route has no rate limit.** Anyone can send random tokens. Each one costs only the `TOKEN_RE` check, or one indexed `calendar_links` lookup by hash when the shape is valid, and returns 404. The 256-bit token can't be guessed. Someone who holds a valid link can fetch it in a loop (three indexed queries and a cached build each time), and `last_fetched_at` is written at most every 15 minutes. | `src/app/api/calendar/[token]/route.ts` | **Accepted** (the same class as S2-10/S3-10). If abuse shows up, a free Vercel firewall rate-limit rule on `/api/calendar/*` is the follow-up. |
| S4-7 | Low | **The feed token is a bearer secret in a URL, stored in plaintext.** The token sits in the path, so it appears in Vercel request logs and is held by whichever calendar provider subscribes. `calendar_links.token` is kept in plaintext so the panel can show the link again (lookup is by SHA-256 hash only). The table has no student or anon privileges and no policies, and the token isn't in the data export (tested). | `20261020000001_step4_timetable_calendar.sql`, `src/server/calendar.ts` | **Accepted** (this is how calendar subscription links work). Reset and turn-off revoke the link at once (reset replaces the hash; turn-off deletes the row), and account deletion cascades. Anyone who can read this table already holds the secret key. |
| S4-8 | Low | **The privacy page didn't say that calendar apps keep a copy.** It said reset or turn-off makes "the old link stop working at once", but Google, Apple and Outlook keep the events they already read until the student removes the calendar there. | `src/app/privacy/page.tsx` | **Fixed** in `0a1311c`. |
| S4-9 | Low | **A student can log made-up study rounds.** `logStudySession` accepts any round that passes the shape checks: up to 3 h, ending no later than now + 5 min, started within the last 30 days, focused time no longer than the round. Rounds may overlap, so a forged call can inflate the student's own "today" and "this week" totals. Nothing is shared or ranked across students, and the 10,000-row cap bounds storage. | `src/server/actions/timer.ts` | **Accepted** (own data only). |

## Checked, no finding
- **Calendar token**: `randomBytes(32)` as base64url (43 characters, 256 bits). The route checks the shape (`TOKEN_RE`) before any lookup. The lookup is by `sha256(token)` with an equality match on a unique index, so the plaintext token is never compared and there is no timing oracle. The database checks the token's shape and that `token_hash` really is its SHA-256 hash. A wrong, old or turned-off token gets the same 404 with no detail, and a database error gets 503 with `Retry-After` and no detail. The response is `Cache-Control: private, no-store, max-age=0`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, with no cookies read. The route is left out of the proxy matcher, so no session refresh runs. `HEAD` does the same as `GET`. The `.ics` suffix is required.
- **Revocation**: "Reset" upserts a new token and hash on the same row, so the old link 404s on the next fetch (e2e "calendar link: make, copy, feed, reset, turn off"). "Turn off" deletes the row. Account deletion cascades through `auth.users` in Supabase, and demo deletes the link too.
- **Feed contents**: the feed has slots only (titles with the subject's emoji, rooms, times, repeats, skipped weeks). It has no notes, study history or email address. The admin reads are pinned to the link's `user_id`, with at most 300 live slots and 200 subjects. `SUMMARY` and `LOCATION` get RFC 5545 TEXT escaping (`\\`, `;`, `,`, newline), and control characters, CR included, are dropped. Lines are folded at 75 octets. `UID` is the slot's uuid, and `CATEGORIES`, `PRODID` and `X-WR-*` are constants. With S4-4 fixed, `TZID` is always a real IANA name.
- **RLS and grants** (local Postgres 16, Supabase-like default privileges): `study_sessions` and `timetable_slots` have RLS on, a `select` policy for their own rows only, and `insert`/`update`/`delete`/`truncate` revoked from `authenticated`, with nothing at all for `anon`. `calendar_links` has RLS on, no policies, and every privilege revoked from `anon` and `authenticated`. I checked `information_schema.role_table_grants` right after the migrations, before the RLS test's blanket grants. The composite foreign keys `(subject_id, user_id)` stop the server from linking a slot or round to another student's subject (tested). The cap triggers (10,000 rounds; 300 live slots plus a 600-row backstop) are `SECURITY INVOKER` with `search_path = ''`, and no role can call them. The checks bound durations, `skip_dates` (60), `import_prev` (8 KB) and title and location (80). `05_grants.sql` (catalog-wide) still passes.
- **New `profiles` columns**: `timer_*`, `focus_quiet` and `week_start` are the student's own preferences. Students may write them directly, under the same policy as `sound_on`/`theme`, and the database checks keep each one in the stepper's range. None of them is server-owned or limits anything.
- **Timer action**: zod checks the uuid client key, the kind, the durations (60 s to 180 min), the ISO times, end after start, 2 days at most, and focused time no longer than the round and its plan. The server refuses rounds that end in the future (beyond 5 min) or are older than 30 days. The subject is checked through the student's repo; another student's id becomes "No subject". The insert is pinned to the student. `unique (user_id, client_key)` makes a retry return the first row, and only the student's own row can come back. B's client key can't collide with A's.
- **Timetable actions**: every slot id is read through RLS (`getSlot`), so another student's id is "not found", and writes are pinned with `user_id`. Subject ids are checked through the repo. `addImport` validates each class the browser sends back again: key `^[A-Za-z0-9_-]{1,64}$`, dates from 2000 to 2100, times and length via `slotError`, at most 60 skipped weeks, no duplicate keys, at most 500 classes. Subject ids are kept only if they are in the student's own list, the zone is always the student's profile zone (never the browser's), and both the action and the trigger enforce the 300-slot cap. `fileKeys` can only make a "Replace" import remove the student's own earlier imports. `previewImport` reads only the uploaded file, never fetches a URL, refuses NUL bytes and anything over 1 MB, saves nothing, and sends the parse error only to the log. The existing test "B can't see, edit, delete, undo or use A's slots and subjects" covers the student-B case.
- **ICS parser**: it reads in a single pass with no backtracking patterns on file content (S4-1 benchmarks). `IANA_INSIDE` is anchored on region prefixes and linear. It reads at most 5,000 events, 100 zones, 50 offsets per zone, 400 `EXDATE`/`RDATE` per event and 2,000 characters per text field, and nesting deeper than 20 levels ends the read. The 500-class cap applies after folding.
- **Service worker** (`public/sw.js`, scope `/`): it has no `fetch` handler and caches nothing. It only focuses or opens a same-origin tab on a notification click. The page acts only on `studynest:open-timer` from its own service worker. The notification text is fixed ("Round done! 🍅 / Time for a N-minute break."), with no subject name or other data on the lock screen.
- **Secrets**: a production build with sentinel values for `SUPABASE_SECRET_KEY`, `GROQ_API_KEY`, `CLOUDFLARE_AI_TOKEN` and `EMBED_FUNCTION_SECRET` has none of them in `.next/static`, and the strings `calendar_links` and `token_hash` aren't there either. `calendar.ts`, `token.ts` and the repos are server-only.
- **Dependencies**: Step 4 adds no dependencies. `npm audit --omit=dev`: 0 vulnerabilities. The full `npm audit` still lists the dev-only `braces` advisory (eslint tooling), which was there before.
