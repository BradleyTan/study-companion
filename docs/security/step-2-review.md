Scope: AI flashcards and mindmaps (Groq, Cloudflare fallback), FSRS review, read aloud, passage links, the read-only source page, migration `20261014000001_step2_flashcards_mindmaps.sql`, and QA open issues A, B and C from `docs/qa/step-2.md`.

## Findings

| S2-1 | Medium | **Students could write flashcards, reviews and mindmaps directly (QA issue A).** The policies were `for all`, so with the publishable key and their own session a student could insert any number of cards and reviews or rewrite schedules and mindmap JSON. That skipped the 2,000-card cap, zod validation and server-side FSRS. The data was their own, but the rows could fill the shared free database (Supabase goes read-only for everyone when it is full). | `supabase/migrations/20261014000001_step2_flashcards_mindmaps.sql:116-121` | **Fixed.** `20261014000002_step2_security_review.sql` replaces them with select-only policies and revokes insert, update and delete from `authenticated`. | S2-2 | Medium | **Failed generations could be retried without limit.** A failure gives the student's go back (`settleAi(..., false)` in the `finally`), but each try still spends the shared app-wide allowance, and up to two provider calls. A note written so the model always returns something unusable (an injection such as "reply with an empty list" is enough) could be retried until the app's AI allowance for the day was gone for every student. There was no cost, because no card is attached, but it was a denial of service. | `src/server/actions/flashcards.ts:117-134`, `src/server/actions/mindmap.ts:56-71` | **Fixed.** `ai_usage.attempts` counts every try, including failed ones. `ai_usage_reserve(..., p_max_attempts)` refuses once either the successful goes (5 flashcard / 3 mindmap) or the tries (15 / 9, `DAILY_ATTEMPTS` in `src/lib/limits/ai.ts`) are used up. The note JSON had no size check in the database. Like S2-1, this let one student fill the free database. | `supabase/migrations/20261011000001_step1_core.sql:40-66`; caps in `src/server/actions/subjects.ts:16`, `notes.ts:15` | **Fixed.** `enforce_row_caps()` insert triggers enforce the same caps in the database. `notes_content_json_size` (≤ 2,000,000 characters of jsonb text, `NOT VALID`, so existing rows aren't re-checked) bounds note JSON. |
| S2-4 | Low | **Disguised prompt delimiters got through.** `defuse` only caught the ASCII spelling of `<passage>` and `</passages>`. Full-width or small-form `＜／ｐａｓｓａｇｅ＞`, a zero-width character or soft hyphen inside the word, HTML entities (`&lt;/passage&gt;`) and `<\/passage>` all passed unchanged, and a model may read any of them as the end of the data block. Severity is low because output validation already confines any successful injection to the student's own data: passage refs map only to passages the server sent, and quotes must be found in those passages. |
| S2-5 | Low | **AI text could carry half an emoji or control characters into the database.** `clip` could cut a surrogate pair in half, and a reply could contain a lone surrogate or a NUL. Postgres refuses such text, so the whole generation failed with a server error after the allowance had been spent. | `src/lib/ai/text.ts` (`clip`) | **Fixed.** `clip` removes lone surrogates and control characters and never cuts through an emoji. |

A student can therefore pull unused goes from yesterday, or borrow tomorrow's, but can't raise their average above the daily limit. At most 3× in one day, then tomorrow's goes are already spent. The app-wide budget is unaffected, and with S2-2 the tries are bounded per key too. | `src/server/ai.ts` (`studentDay`) | **Accepted** (borrowing, not a reset). Switching to a UTC day key would remove it but would reset the "left today" chip in the middle of a student's day. Revisit if usage data shows abuse. |

Every admin query is pinned to the student's id and note, and the composite foreign keys hold, so nothing can cross students. | `src/server/repo/supabase.ts` (`replaceNoteChunks`) | **Open, developer** (with QA issue D). ## Checked, no finding
- **Server actions** (`flashcards.ts`, `review.ts`, `mindmap.ts`): every argument is zod-validated (uuids, literal counts, page ranges ≤ 20, ratings 1–4, client keys). Every id is resolved through the student's own RLS-scoped reads before use: subject, note, file, chunk, card and mindmap. A second student's ids are refused or ignored. This is proven in `src/server/actions/security.test.ts` for all 14 entry points, including `?quote=` / `?card=` (`passageTarget`) and `getPassage`. `saveMindmapPositions` only accepts known ids (`n\d{1,3}`, ≤ 40 entries, ±100,000 px) and re-validates the whole graph.
- **Citations**: the model only ever sees `p1…pN`. `resolvePassage` maps them only to passages the server sent, and `cardsToSave` re-checks every chunk id against the passages it picked. A foreign uuid, `p99`, unknown fields (`chunkId`, `user_id`, `href`) and oversized arrays are dropped or rejected (`src/lib/ai/injection.test.ts`, 32 cases). The AI cache is keyed per student (`ai_cache` primary key includes `user_id`; reads are RLS-scoped) and is re-validated against the current passages on reuse.
- **Quota functions**: `ai_usage_reserve`/`settle`, `ai_app_reserve` and `ai_app_add_tokens` are `SECURITY INVOKER` with `search_path = ''`. Execute is revoked from `public`, `anon` and `authenticated` and granted only to `service_role`. The RLS tests call each one as a student and expect `insufficient_privilege`. `ai_app_usage` has RLS on, no policies and no grants.
- **Secrets**: `GROQ_API_KEY`, `CLOUDFLARE_AI_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are read only in `src/lib/ai/providers.ts` (`server-only`). A production build with sentinel values for them and for `SUPABASE_SECRET_KEY` has none of the values, and neither `api.groq.com` nor any key name, anywhere in `.next/static` (the values are not inlined into server output either). Provider errors log nothing; the request body (student text) is never logged.
- **Read aloud**: `pickVoice` prefers on-device voices (`localService`) and falls back to online ones only when the device has none. Online voices are labelled "(online)" with the hint "Online voices send the text to your browser's maker". Nothing is sent by StudyNest.
- **Rendering**: card text, quotes, labels and passages are rendered as React text. There is no `dangerouslySetInnerHTML` (only the constant theme script) and no auto-linking, so a hostile file can't inject markup.
- **`/review`** is in the proxy's protected list. `npm audit --omit=dev`: 0 vulnerabilities.

- `src/server/repo/demo.test.ts`: the tries cap.

The server path works and still can't cross students via the foreign keys. The tries cap is checked, `ai_app_add_tokens` and `enforce_row_caps` can't be called by students, and the 51st subject, the 501st note and oversized note JSON are refused. ## Not covered here
- **Real models**: prompt injection against real Groq and Cloudflare replies needs a free key in a preview deploy (QA's list). Output validation is what keeps it to the student's own data. Injection itself can't be fully prevented, so a hostile lecture file can still produce misleading cards for the student who uploaded it.
- **Live project**: not touched. After `20261014000002` is applied to the live project, run the Supabase security advisor and re-run the two-student checks, as for Step 1.
