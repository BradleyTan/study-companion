## Checked, no finding
- **Validation**: `addWeakTopicInput` checks `subjectId` as a uuid and the topic as a string of at most 400 characters before `cleanTopic` runs (bounded work), then 1 to 40 characters after. Non-strings, `null` and bad ids are refused (tests).
- **Ownership**: the subject is read through the student's own repo (`getSubject` on the RLS-scoped client; demo is per-user), so another student's subject is "Subject not found." and nothing is written (test). The existing row comes from `findWeakTopic` on the same scoped client.
- **Write path**: students still have no insert/update on `weak_topics` (revoked in `20261018000001`). The server writes with the secret key, insert pinned to `user_id: userId` from the session and update filtered by `.eq("user_id", userId)`. The composite FK `(subject_id, user_id) → subjects (id, user_id)` stops a row pointing at another student's subject even if the server check were skipped.
- **Cap and races**: the server counts before inserting (500) and the `weak_topics_cap` trigger is the backstop; the trigger's message is mapped to the same friendly error. Two tabs adding the same topic: the `unique (subject_id, user_id, topic_key)` key rejects the second insert, which is re-read and reported as "already on your list". Under READ COMMITTED two simultaneous inserts at 499 could both pass the trigger (501 rows); that is the pre-existing backstop behaviour, bounded and harmless.
- **Key match**: `cleanTopic` collapses all whitespace, so the database key `lower(btrim(topic))` and `topicKey()` agree; any rare Unicode case-folding difference only produces "Couldn't add that", never a cross-row write.
- **Rendering**: topic names render only as React text (`TopicNote` heading, quiz builder list, `aria-label` free). No new `dangerouslySetInnerHTML`, URL or attribute built from the name; the toast text is fixed.
- **Prompt injection**: a hand-added name reaches the model only through `quizMessages` `focus`: in the user message, as JSON-quoted data, `defuse`d and cut to 40 characters, with the system rules saying it is data. `focus` now holds only topics that have passages, so a topic with no notes never reaches the model. The keyword search passes the name as a bound RPC parameter into `plainto_tsquery` (no tsquery syntax, no SQL). Replies are validated by `normaliseQuizWithStats` as before; passage refs map only to chunks the server sent. The worst case is a misleading question in the student's own quiz.
- **Quota**: `weak_no_notes` (and `weak_gone`) return before `reserveAi`, the AI cache and `runAiTask`; tests check the daily count stays 0 with no matching notes and with no notes at all. Focus keys are part of the cache hash, so a different topic set can't reuse another quiz's cached reply.
- **Undo of a miss**: `undoMiss` now keeps a row that existed before the miss (hand-added) with 0 misses instead of deleting it; a row created by the miss is still deleted. Same student, same row, pinned update.
- **Abuse / rate limit**: adding a topic uses no AI and no paid service: four small owner-scoped queries and one row of at most 60 characters, capped at 500 per subject (subjects are capped at 50). No separate rate limit is needed; the general per-student function-invocation concern is the same as any other server action.
- **Dependencies**: `package.json` and `package-lock.json` unchanged; `npm audit` 0 vulnerabilities.
- **RLS**: no migration, so `npm run test:db` was not re-run (no `DATABASE_URL` here).
