| S3-1 | Medium | **Chat reply parsing took seconds of server CPU on a run of spaces (ReDoS).** `REF_GROUP` reads citation groups such as `[p1, p3]`. The text is the model's reply, which a hostile note or lecture file can steer, and spaces are cheap in tokens. The cached reply is parsed again on every repeat question. ## Checked, no finding
- **RLS and grants** (local Postgres 16 with pgvector, throwaway database, Supabase-like default privileges): every new table (`quizzes`, `questions`, `quiz_attempts`, `answers`, `weak_topics`, `chat_messages`) has RLS on and only a `select` policy `user_id = auth.uid()`. Insert, update, delete and truncate are revoked from `authenticated`, and everything is revoked from `anon`. `questions` is readable only through a column grant that leaves out `answer`, `correct_index`, `accepted_json`, `explanation` and now `source_quote`. Composite foreign keys `(x_id, user_id)` stop even the server from linking a row to another student's subject, quiz, question, attempt, note, file, passage or chat question (tested). The cap triggers (200 quizzes per subject, 20 questions per quiz, 50 attempts per quiz, 500 weak topics per subject, 1,000 chat messages per subject) are `SECURITY INVOKER` with `search_path = ''`, and no role can call them. jsonb and array size checks bound `options_json`, `accepted_json`, `order_json`, `weak_prev`, `citations_json`, `chunk_ids` and `recent`.
- **Retrieval functions**: `search_chunks` and `match_chunks` are `SECURITY INVOKER` and `search_path = ''`. They filter `user_id = auth.uid()` on top of chunks RLS, cap the row count (50 and 20), can be called by `authenticated` only, and the server calls them with the student's own session. B gets no rows for A's subject, and `anon` can't call them (tested). `plainto_tsquery` treats query syntax as plain text (tested with `') | ('x' & !'y`).
- **Server actions** (16 entry points in `quiz.ts`, `weak-topics.ts`, `chat.ts`): every argument is validated with zod (uuids, literal counts and kinds, page ranges ≤ 50, choice 0–3, text ≤ 200, question ≤ 500, topics ≤ 100 × 40, edit fields at the database limits). Every id is resolved through the student's own repo: RLS-scoped reads, or secret-key reads pinned with `user_id`. A question must belong to the attempt's quiz and be in the attempt's order. A client key reused on another question or attempt is refused (`unique (user_id, client_key)`; the server checks that the returned answer is this question's). Results are refused until the attempt is finished. The new `src/server/actions/security-step3.test.ts` runs student B against every Step 3 action with A's ids and checks that nothing is changed or leaked. It also mixes ids from two quizzes of one student, and reuses a client key across questions.
- **Answers hidden until checked**: `playView` sends only `id`, `type`, `prompt`, `options` (shuffled for the attempt) and `topic`. Answers, explanations and quotes only go out in the feedback for an answered question or in finished results (QA's e2e network check, and the unit test). The stored option order is shuffled by the server, so `options_json` plus the attempt's `o` permutation don't reveal `correct_index`.
- **Prompt injection**: passages, existing and focus topic names, the subject name, the chat question and the last 4 messages all go in the user message as quoted, defused JSON or `<passage>` blocks. Only the fixed rules are in the system message. Quiz output is zod-validated, capped at 60 items and clipped to the database limits. Passage refs map only to passages the server sent; a ref to any other passage drops the question. Answers, filled sentences and explanations must be grounded in the cited passage and must not swap a passage term. Chat sentences keep only refs to passages that were sent, and must be grounded and swap-free. Citations map refs to the student's own chunk ids, and quotes are re-derived from the passage (`bestSentence`), not taken from the model. Cached replies are validated again on reuse. A successful injection can only produce misleading questions or answers about the uploading student's own notes.
- **Citations and links**: `passageHref` builds every link from the page's subject id and the note or file ids found in the student's own lists. `chunkId` is used only when `getChunks` (RLS) still finds it. A citation whose note or file is gone has no link. The citation preview loads text through `getPassage` (reviewed in Step 2, RLS-scoped).
- **XSS**: chat answers are parsed into plain data (paragraphs, lists, bold, citation numbers) and rendered as React text nodes. HTML, links, images and code are stripped first. Quiz prompts, options, explanations, quotes, topic names and citation labels are React text. The app's only `dangerouslySetInnerHTML` is still the constant theme script. QA's e2e test puts `<img onerror>` in a note and checks the answer and the preview.
- **Quota**: `reserveAi` (atomic, `service_role` only) runs before every model call and before chat retrieval, so embedding and keyword searches are bounded by the 60 tries a day. A not-covered answer found without the model, a cached answer and a failure all give the go back, but the try stays counted. A retried send with the same client key returns the stored exchange without a new try, and a concurrent duplicate fails on the unique key and is refunded. "Quiz me" is never cached. The app-wide budget is reserved per model and per provider attempt in `runAiTask`.
- **ReDoS**: besides S3-1, I benchmarked the fill-in matcher, `standardBlanks`, the quiz normaliser (60 questions at maximum field sizes), `keyTerms`/`rankByKeywords`, `isQuizMe`, `topicKey`, `parseContent` and `plainText` on 21 adversarial generators at 2,000 and 20,000 characters. Everything other than S3-1 is linear or bounded by field clipping: the quiz normaliser takes at most 300 ms for 60 questions at 20,000-character inputs, and real replies are capped at 4,000 tokens.
- **Secrets**: a production build with sentinel values for `GROQ_API_KEY`, `CLOUDFLARE_AI_TOKEN`, `EMBED_FUNCTION_SECRET` and `SUPABASE_SECRET_KEY` has none of them in `.next/static`, and neither do `api.groq.com` or the model names. `embed.ts` and `providers.ts` are `server-only`.
- **Export and account deletion**: `exportAll` includes quizzes, questions (with answers, read with the secret key, pinned), attempts, answers, weak topics and chat messages. Every new table references `auth.users` with `on delete cascade`, so account deletion removes them all (`10_rls.sql` checks the subject cascade). The privacy page lists quizzes, answers, weak topics, chat, embeddings and the limit of 1,000 messages.
- **Routes**: `/subjects/...` (quizzes, weak topics, ask) is in the proxy's protected list, and every page checks the subject through the student's repo. `?attempt=` is validated as a uuid and must belong to the quiz.
- `npm audit --omit=dev`: 0 vulnerabilities. There are no dependency changes in Step 3. The full `npm audit` still lists the dev-only `braces` advisory (eslint tooling), which was there before.
